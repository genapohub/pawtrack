# 宠迹 PawTrack — 定位数据缓冲层设计

> 版本：V1.1 | 首次：2026-07-21 | 更新：2026-08-09  
> 解决：高频定位数据写入性能瓶颈  
> 状态：✅ 已落地（location.py 使用 Redis Stream `location:stream` + GEO `location:geo:nearby` + Pub/Sub 推送）

---

## 1. 问题背景

### 1.1 数据量预估

| 指标 | 数值 | 计算 |
|------|------|------|
| 活跃设备数（MVP目标） | 10,000 台 | 3万月活 × 30% 设备激活率 |
| 上报间隔 | 10秒（默认） | 狗狗版GPS模式 |
| 日上报量 | **8,640万条** | 10,000 × 8640次/天 |
| 峰值写入 | **~1,500 QPS** | 早/晚遛狗高峰，集中时段 |
| MongoDB 单集合适配 | ~2万 QPS | 可支撑，但无缓冲风险高 |

### 1.2 无缓冲的风险

```
设备 ────→ MongoDB
      ① 直接写

风险：
1. MongoDB 抖动/慢查询 → 写入堆积 → 队列超时 → 数据丢失
2. 无背压机制 → 设备端重试导致更多写入 → 雪崩
3. 无法做批量写入优化 → 单条写入效率低
4. 会员/免费差异化存储需要应用层额外代码
```

---

## 2. 方案选型：Redis Stream

### 2.1 为什么选 Redis Stream 而非 Kafka

| 维度 | Redis Stream | Kafka |
|------|-------------|-------|
| 运维复杂度 | ⭐ 低（Redis 已引入） | ⭐⭐⭐ 需独立集群 |
| 学习成本 | ⭐ 低 | ⭐⭐⭐⭐ |
| MVP阶段适配 | ✅ 可用现有 Redis 实例 | ❌ 额外资源 |
| V2/V3 扩展性 | 有限（单节点瓶颈） | ✅ 高吞吐 |
| 消息持久化 | 可选 AOF/RDB | ✅ 强制持久化 |
| 可靠性 | 至少一次 | 精确一次 |

**结论**：MVP 阶段选 **Redis Stream**（零额外基础设施），V2 规模扩张后迁移到 **Kafka**。

### 2.2 架构设计

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   设备端      │     │   定位服务     │     │  消费者组     │
│              │     │              │     │              │
│ MQTT上报定位  │────▶│ 写入 Redis    │────▶│ 消费者1:      │
│ 数据          │     │  Stream      │     │ → MongoDB    │
│              │     │              │     │ （原始轨迹）   │
│              │     │  Redis        │     │              │
│              │     │  GEO 更新     │     │ 消费者2:      │
│              │     │ （实时位置）    │     │ → PostgreSQL  │
│              │     │              │     │ （会员归档）    │
│              │     │              │     │              │
│              │     │              │     │ 消费者3:      │
│              │     │              │     │ → 围栏检测    │
│              │     │              │     │ → WebSocket推送│
└──────────────┘     └──────────────┘     └──────────────┘
```

## 3. 详细设计

### 3.1 Redis Stream 配置

```yaml
stream:
  name: location:stream           # Stream 名称
  maxlen: ~1000000                 # 最大保留 100 万条（约 2 分钟数据）
  approximate: true                # 近似截断（性能优于精确截断）

consumer_groups:
  - name: location:group:mongo    # MongoDB 写入消费者
    consumer_count: 3              # 3 个消费者并行
  - name: location:group:archive  # 会员归档消费者
    consumer_count: 2
  - name: location:group:fence    # 围栏检测消费者
    consumer_count: 2
```

### 3.2 消息格式

```json
// Redis Stream 中的消息体（与 MQTT 上报格式一致）
{
  "device_id": 1001,
  "pet_id": 67890,
  "user_id": 12345,
  "member_level": "pro",         // 会员等级（不同等级不同存储策略）
  "lat": 31.2304,
  "lng": 121.4737,
  "accuracy": 5.0,
  "altitude": 12.0,
  "speed": 0.5,
  "source": "gps",
  "is_indoor": false,
  "battery": 85,
  "ts": 1721532000,
  "seq": 1024                    // 设备序列号（去重）
}
```

### 3.3 消费者逻辑

#### 消费者 1：MongoDB 写入

```python
async def consume_location_to_mongo():
    """批量写入 MongoDB（每 1 秒写入一次，减少连接开销）"""
    batch = []
    last_flush = time.time()
    
    while True:
        # 从 Redis Stream 读取新消息（阻塞等待，最多 1 秒）
        messages = await redis.xreadgroup(
            group_name='location:group:mongo',
            consumer_name='mongo-1',
            streams={'location:stream': '>'},
            count=100,          # 每次最多读 100 条
            block=1000          # 阻塞最多 1 秒
        )
        
        for msg_id, msg_data in messages:
            batch.append(parse_location(msg_data))
        
        # 每 1 秒或每 500 条批量写入 MongoDB
        if len(batch) >= 500 or time.time() - last_flush >= 1:
            if batch:
                await mongo.locations.insert_many(batch, ordered=False)
                # 批量确认已消费的消息
                await redis.xack('location:stream', 'location:group:mongo', *msg_ids)
            batch = []
            last_flush = time.time()
```

#### 消费者 2：会员轨迹归档

```python
async def consume_to_archive():
    """Pro 用户轨迹同步到 PostgreSQL（永久保留）"""
    batch = []
    
    while True:
        messages = await redis.xreadgroup(
            group_name='location:group:archive',
            consumer_name='archive-1',
            streams={'location:stream': '>'},
            count=100,
            block=1000
        )
        
        for msg_id, msg_data in messages:
            # 只处理 Pro 会员
            if msg_data['member_level'] in ('basic', 'pro'):
                batch.append({
                    'device_id': msg_data['device_id'],
                    'pet_id': msg_data['pet_id'],
                    'location': f'POINT({msg_data["lng"]} {msg_data["lat"]})',
                    'accuracy': msg_data.get('accuracy'),
                    'source': msg_data.get('source'),
                    'created_at': datetime.fromtimestamp(msg_data['ts'])
                })
        
        if len(batch) >= 200:
            # 批量 INSERT（使用 COPY 语句更高效）
            await pg.copy_records_to_table(
                'locations_archive',
                records=batch,
                columns=['device_id', 'pet_id', 'location', 'accuracy', 'source', 'created_at']
            )
            batch = []
```

#### 消费者 3：围栏检测

```python
async def consume_to_fence_check():
    """实时围栏检测（每 1 秒执行一次批量查询）"""
    batch = set()  # 去重：同一设备同一秒多次上报只检一次
    
    while True:
        messages = await redis.xreadgroup(
            group_name='location:group:fence',
            consumer_name='fence-1',
            streams={'location:stream': '>'},
            count=200,
            block=1000
        )
        
        for msg_id, msg_data in messages:
            batch.add(msg_data['device_id'])
            update_realtime_geo(msg_data)  # 同步更新 Redis GEO
        
        if batch and len(batch) >= 50:
            await batch_fence_check(list(batch))  # 批量 PostGIS 查询
            batch = set()
    
    # 每 1 秒强制检查一次
    if batch:
        await batch_fence_check(list(batch))
        batch = set()

async def batch_fence_check(device_ids: list):
    """批量 PostGIS 围栏检测"""
    sql = """
        SELECT p.id, p.user_id, d.id as device_id
        FROM pets p
        JOIN devices d ON d.pet_id = p.id
        JOIN locations_archive la ON la.device_id = d.id
        WHERE p.fence_enabled = true
          AND d.id = ANY($1)
          AND la.created_at = (
              SELECT MAX(created_at) FROM locations_archive 
              WHERE device_id = d.id
          )
          AND NOT ST_DWithin(
              p.fence_center::geography,
              la.location::geography,
              p.fence_radius
          )
    """
    results = await pg.fetch(sql, device_ids)
    for row in results:
        await trigger_alarm(row['id'], row['user_id'], row['device_id'])
```

### 3.4 端到端数据流

```
Timeline (每秒):

Ms 0    设备上报定位 (MQTT)
         │
Ms 1-5  定位服务解析 → 写入 Redis Stream
         │
Ms 6    消费者1: 批量写入 MongoDB (每 1s / 500条)
         │       → Redis GEO 更新 (实时查询用)
Ms 6    消费者2: Pro用户 → PostgreSQL locations_archive
         │
Ms 6    消费者3: 围栏检测 → 触发报警 → WebSocket推送
         │
Ms 7    恢复正常 (总耗时 < 1s)
```

### 3.5 故障恢复

| 故障场景 | 恢复策略 |
|---------|---------|
| MongoDB 不可用 | 暂停消费者1，消息堆积在 Redis Stream，MongoDB 恢复后追写入 |
| PostgreSQL 不可用 | 暂停消费者2，仅影响 Pro 会员归档（不影响核心功能） |
| Redis 宕机 | 数据丢失（最新 2 分钟的位置），设备端重新上报 |
| 消费者崩溃 | Redis Stream 自动重新分配未确认消息给其他消费者（PEL 机制） |
| 消费失败（3次） | 移入 Dead Letter Stream，人工介入处理 |

## 4. 成本与扩展

### 4.1 Redis 内存估算

| 数据量 | 单条大小 | 100 万条 | 200 万条（峰值） |
|--------|---------|----------|----------------|
| Redis Stream | ~200 bytes | ~200 MB | ~400 MB |
| Redis GEO + 实时位置 | ~64 bytes × 1万 | ~0.64 MB | ~0.64 MB |
| **合计** | | **~200 MB** | **~400 MB** |

MVP 阶段 4GB Redis 实例完全够用。

### 4.2 V2 迁移到 Kafka 方案

```
V1 ← Redis Stream（MVP，零额外基础设施）
  │
  ├─ 信号：日均定位数据量 > 5亿条 或 Redis 内存 > 2GB
  │
  └─ V2 ← Kafka（高性能、高吞吐）

Kafka 配置：
  topic: pawtrack.location
  partitions: 6（可水平扩展）
  retention: 24h（容灾）
  consumer_group: location-processor
  replication: 3（高可用）
```

```markdown
### 2.4.2 定位数据写入缓冲

MVP 阶段使用 **Redis Stream** 作为定位数据缓冲层，解决高频写入性能瓶颈：

```
设备 MQTT 上报 → 定位服务 → Redis Stream(缓冲) → 消费者组
                                                       │
                                            ┌──────────┼──────────┐
                                            ▼          ▼          ▼
                                        MongoDB    PostgreSQL  围栏检测
                                      (原始轨迹)   (会员归档)   (报警推送)
```

- 3 个消费者组独立处理，互不影响
- 批量写入（每 1 秒或每 500 条），减少数据库连接开销
- 故障隔离：任一存储故障不影响其他消费者
- V2 阶段迁移到 Kafka
```

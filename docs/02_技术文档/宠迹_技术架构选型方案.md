### 2.3 数据库选型

| 用途 | 选型 | 理由 |
|------|------|------|
| 业务数据（用户/宠物/设备/订单） | **PostgreSQL 16 + PostGIS 3.4** | 关系型、ACID、JSONB 支持、GIS空间查询扩展 |
| 实时定位缓存 | **Redis 7** | 高速读写、有序集合 + 地理索引 GEO |

### 2.4 实时定位数据推送方案

```
设备(GPS/BLE) → MQTT Broker(EMQX) → 定位服务 → Redis(实时位置)
                                               ↓
                                     WebSocket Server → App客户端

定位数据流：
  1. 设备每5-30秒上报GPS坐标（MQTT QoS 1）
  2. 定位服务写入 MongoDB（原始轨迹）+ Redis Geo（实时查询）
  3. 会员用户同时写入 PostgreSQL locations_archive（永久归档）
  4. 通过 WebSocket 实时推送位置更新到订阅者
  5. 围栏检测（见 2.4.1）→ 触发报警服务 → Push通知
```

#### 2.4.1 围栏检测方案（PostGIS 服务端检测）

```
方案：定时任务扫描 + PostGIS ST_DWithin 空间函数

1. 设备上报位置 → 更新 pets.fence_center 缓存到 Redis Geo
2. 每秒定时任务：
   SELECT p.id, p.user_id, p.fence_radius
   FROM pets p
   JOIN devices d ON d.pet_id = p.id
   JOIN locations l ON l.device_id = d.id
   WHERE p.fence_enabled = true
     AND l.created_at > NOW() - INTERVAL '10 seconds'
     AND NOT ST_DWithin(
       p.fence_center::geography,
       l.location::geography,
       p.fence_radius
     )
3. 超出围栏 → 写入 alarms 表 → 推送报警通知
```

> **为什么用 PostGIS 而不是 Redis Geo？**
> Redis Geo 只支持"附近N米内的点"查询，不支持"某点是否在某半径内"的反向检测。
> PostGIS `ST_DWithin` 原生支持围栏检测，且有空间索引加速，精度更高。

## 3. 基础设施规划

### 3.1 MVP 阶段架构（单机可扩展）

- **部署方式**：Docker Compose 部署在 1 台 ECS
- **服务拆分**：API 服务 + 定位服务 + 后台服务（3个进程）
- **数据库**：RDS PostgreSQL + Redis + MongoDB
- **CI/CD**：GitHub Actions → Docker Build → ECS 部署

### 3.2 V2 阶段架构（微服务化）

- 容器化：K8s（ACK / 自建 K3s）
- 服务拆分：6个微服务独立部署
- 自动扩缩容：HPA + 负载监控
- 蓝绿部署 / 灰度发布

### 5.6 Sprint 3 交付物（v0.4.0）

**后台管理系统**
- 后端 admin 路由（登录 / dashboard / 用户·宠物·设备·报警·订单 CRUD / 编辑 / 批量处理）
- admin 前端（Vite + React + antd）：6 页，支持编辑弹窗、批量处理、CSV 导出

**测试用例**
- 后端 pytest：JWT 鉴权逻辑、模型枚举与套餐、API 集成测试（25 passed, 8 skipped）
- 前端 Vitest：mobile + admin API 客户端测试

**CI/CD 流水线**
- `.github/workflows/ci.yml`：三端 lint / test / build（Python 3.12 + Node 22）
- `.github/workflows/docker-publish.yml`：tag 触发，多架构（amd64+arm64）镜像推送 GHCR
- `.github/workflows/load-test.yml`：手动触发压测 workflow
- 生产 Dockerfile（多阶段构建）+ nginx 反代 + .dockerignore

**多环境自动切换**
- `config.py` 环境分层：ENV=dev|prod 自动选择默认值，prod 启动校验（拒绝默认密码/localhost）
- `docker-compose.infra.yml`（本地裸跑基础设施）/ `docker-compose.yml`（全栈开发）/ `docker-compose.prod.yml`（生产）
- 前端 vite 多 mode + UI 环境标签（避免误操作生产数据）
- Makefile 一键命令（make dev / prod / test / load-test / keys）

**监控告警接入**
- 结构化日志（dev 彩色 / prod JSON，按环境分级）
- 深度健康检查 `GET /health`（并发检查 DB/Redis/MongoDB 连通性）
- Prometheus 指标 `GET /metrics`（prometheus_fastapi_instrumentator）
- 请求中间件（X-Request-ID + 耗时日志 + 慢请求告警 + 全局异常处理）
- Sentry 集成（SENTRY_DSN）+ 告警 webhook（ALERT_WEBHOOK_URL）

**性能压测方案**
- Locust 压测脚本（MobileUser / DeviceReport / AdminUser 三类虚拟用户）
- 数据库索引优化（补充 5 个复合索引覆盖 admin 筛选与热点查询）
- 性能基线定义（登录 P95<200ms、位置上报 P95<50ms、错误率<0.5%）

**API 接口全量补全（对照设计文档 100% 覆盖）**
- 用户模块（users.py）：me / 更新 / 密码 / 设备 / 注销
- 限流中间件（ratelimit.py）：登录 5/min、定位 30/min、全局 300/min
- 订单补全：订单详情 / 发起支付 / 续费
- 宠物围栏查询 GET /pets/{id}/fence
- 报警设置 GET/PUT /alarms/settings
- 设备接口骨架：unbind / config / find / status / ota / ota/progress

**关键 Bug 修复（测试驱动发现）**
1. JWT 密钥对不匹配（dev 环境生成两对独立密钥）→ 改为单一密钥对
2. refresh token 缺少 audience → 补上 aud: pawtrack-app
3. models.py BIGINT/BIGSERIAL 导入缺失 → 统一改为 BigInteger（跨版本兼容）
